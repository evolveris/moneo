# ADR-003: Data model on Postgres

- Status: Proposed
- Date: 2026-11-13
- Answers: ADR-001 open decision 1 (data model), on the database chosen in ADR-002

## Context and problem statement

Slices 05 to 07 write transactions to Postgres, so the tables, keys and rules must be decided first. This ADR decides the shape of the data. It creates no tables and changes no code; the first migration comes in slice 05.

What the model has to support, from the SPEC and the decision log:

- A demo visitor gets their own copy of the demo data, keyed by a cookie, expiring after 24 hours of inactivity, and Reset wipes only that copy (D-005, D-030).
- A transaction keeps the original imported date, amount and description next to the current ones. Duplicate detection matches on the originals, by count, plus the running balance when the file has one (D-034, D-035).
- A category can be changed for all stored transactions of the same merchant, with undo (D-021, D-022). A transaction may carry a clean merchant name (D-046).
- A context (mood, motivation, optional outcome, optional note) is complete or absent (D-044). Deleting a transaction deletes its context.
- The categories, moods, motivations and outcomes are fixed lists (D-042) held in `src/domain/lists.ts`.
- The 5,000-row transaction list must stay fast (ADR-001 constraint 4).
- The AI later writes derived labels back, kept apart from what the user entered (D-036).
- You and your partner will later add your own motivation to the same purchase (J11, after auth).

The data is a set of tables joined by single hops from the transaction (see ADR-002), which is why a relational model fits.

## Decision

### Tables

```sql
create table visitor (
  id           uuid primary key default gen_random_uuid(),
  created_at   timestamptz not null default now(),
  last_seen_at timestamptz not null default now()
);

create table import (
  id          uuid primary key default gen_random_uuid(),
  visitor_id  uuid not null references visitor (id) on delete cascade,
  source_type text not null check (source_type in ('csv', 'pdf', 'receipt')),
  created_at  timestamptz not null default now(),
  unique (visitor_id, id)
);

create table transaction (
  id                      uuid primary key default gen_random_uuid(),
  visitor_id              uuid not null references visitor (id) on delete cascade,
  import_id               uuid not null,
  date                    date not null,
  amount_pence            integer not null,
  description             text not null check (btrim(description) <> ''),
  category                text not null check (category in (
    'Groceries', 'Eating out', 'Transport', 'Housing', 'Bills and utilities',
    'Subscriptions', 'Shopping', 'Health and fitness', 'Other', 'Income',
    'Transfers'
  )),
  category_source         text not null check (category_source in ('ai', 'user')),
  merchant_key            text not null,
  merchant_name           text,
  original_date           date not null,
  original_amount_pence   integer not null,
  original_description    text not null,
  running_balance_pence   integer,
  source_type             text not null check (source_type in ('csv', 'pdf', 'receipt')),
  created_at              timestamptz not null default now(),
  unique (visitor_id, id),
  foreign key (visitor_id, import_id)
    references import (visitor_id, id) on delete cascade,
  check (category <> 'Income' or amount_pence >= 0)
);

create index transaction_visitor_date on transaction (visitor_id, date desc);
create index transaction_visitor_merchant on transaction (visitor_id, merchant_key);
create index transaction_visitor_original on transaction (
  visitor_id, original_date, original_amount_pence, original_description
);

create table context (
  id             uuid primary key default gen_random_uuid(),
  transaction_id uuid not null,
  visitor_id     uuid not null,
  mood           text not null check (mood in (
    'happy', 'stressed', 'bored', 'sad', 'anxious', 'excited', 'calm', 'tired'
  )),
  motivation     text not null check (motivation in (
    'need', 'planned', 'habit', 'impulse', 'treat', 'social pressure',
    'deal or sale', 'social media', 'unwell'
  )),
  outcome        text check (outcome in (
    'glad I bought it', 'regret it', 'used it', 'unused', 'returned', 'sold'
  )),
  note           text check (char_length(note) <= 200),
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now(),
  unique (transaction_id),
  foreign key (visitor_id, transaction_id)
    references transaction (visitor_id, id) on delete cascade
);
```

This is a sketch of the shape, not the migration. Slice 05 writes the real migration.

### Why these choices

- **Visitor scope.** Every table carries `visitor_id`. Composite foreign keys, such as `(visitor_id, import_id)` and `(visitor_id, transaction_id)`, make it impossible for a row to point at a parent that belongs to another visitor. The first rule of AGENTS.md still applies on top: every data function takes `visitorId` as a required argument and every query filters on it. Row-level security (the database refusing cross-visitor reads even when a query forgets the filter) is not used now, because it needs a separate non-owner database role and a visitor setting per transaction, which fits Neon's one-request-per-query HTTP driver awkwardly. It can be added later without changing the tables.
- **Expiry and reset.** A scheduled job deletes `visitor` rows whose `last_seen_at` is older than the expiry window (24 hours, kept in the config file). Reset deletes the visitor's imports, which cascade to transactions and contexts. Because every child cascades from `visitor` or `import`, no cleanup query has to name the children.
- **Merchant is a column, not a table.** `merchant_key` is the output of `merchantKey()` in `src/domain/derived.ts` (D-022), computed in code once after import and never changed, with no AI (ADR-001 open decision 15). "Apply to the same merchant" is one `update … where visitor_id = $1 and merchant_key = $2`. `merchant_name` is the optional clean name (D-046). If AI naming is added later, a merchant table can be introduced then.
- **Context is its own table.** It is one row per transaction today (`unique (transaction_id)`), which keeps the SPEC's "complete or absent" rule: `mood` and `motivation` are `not null`, and no row means no context. When J11 arrives, an author column is added and the unique key becomes `(transaction_id, author_id)`, so a second person can add their own context to the same purchase without moving data. The cost is a join in the list and the charts.
- **Original values are plain columns.** Date, amount and description are kept as three columns next to the current ones, so duplicate matching is an indexed lookup (`transaction_visitor_original`) and an "edited" marker is a comparison. Matching is by count (D-035): the importing code counts stored rows per original key and treats up to that many incoming identical rows as duplicates.
- **The fixed lists are text with CHECK constraints.** The code lists in `src/domain/lists.ts` stay the source of truth for the UI and for Zod. The database repeats them as constraints so bad data cannot get in by another route. A list change needs a migration. Slice 05 adds a test that the migration's lists equal the code lists, so they cannot drift apart.
- **Money and dates.** Amounts are `integer` pence (up to about £21 million, plenty for one person's transactions). Dates are `date`. The Neon driver's return type for `date` must be checked in slice 05, so that the app still sees the `YYYY-MM-DD` string that `DateSchema` expects.
- **Ids** are `uuid` with `gen_random_uuid()`, available in Postgres without an extension.
- **Indexes** match the queries the SPEC needs: the transaction list by visitor and date, same-merchant overrides, and duplicate lookup.

### Reserved for later, not created now

- **AI-derived data (D-036).** A separate table keyed by transaction and kind, marked as AI-made, deleted with its transaction. It keeps what the AI produced apart from what the user entered, so it can be inspected, corrected or deleted. The table is created when the agentic journey and its label list are written.
- **AI usage counters (D-008, D-032).** The hourly per-visitor limit and the global daily cap need a table of AI calls. Its rows must not cascade from `visitor`, or clearing cookies and expiry would reset the global cap. Planned for slices 08 and 15.
- **LangGraph checkpoints** live in a separate schema managed by the library (ADR-001 open decision 9).

## Consequences

- **Good:**
  - Deleting a transaction, an import or a visitor is one statement; the schema removes the children.
  - A child row cannot belong to a different visitor than its parent.
  - Charts and lists are plain `group by` and `join` queries on indexed columns.
  - The J11 change to `context` is small and known in advance.
- **Bad / trade-offs accepted:**
  - Without row-level security, one query that forgets the visitor filter still reads other visitors' rows. Tests and the required `visitorId` argument are the safety net.
  - Fixed lists exist in two places (code and database constraints), and a list change needs a migration.
  - Reading a transaction with its context needs a join.
  - Dates and money need checking at the driver boundary.

## Decided by the author after review

1. **Merchant key is set once.** `merchant_key` is computed by `merchantKey()` right after import and is never recomputed, even when the description is edited. "Same merchant" therefore means "the same cleaned name at import", not what the row shows now. Grouping by merchant name in the UI is not wanted yet.
2. **Running balance is stored.** `running_balance_pence` stays in the table, and `TransactionSchema` gets an optional `runningBalancePence` field (D-035 duplicate matching uses it). The code change is a separate small pull request, not part of this ADR.

## Open decisions (to be answered by the author)

1. **Which fields can be edited.** The SPEC (D-034) lets the user edit date, amount and description on stored transactions. The author wants description and amount editable, is unsure about date, and is unsure about editing bank rows at all. The tables do not depend on the answer (the originals are kept either way), but the SPEC needs a decision before the inline-editing slice (10).
2. **Migrations.** Which tool applies them and how they run on the `dev` and `main` branches (ADR-002 open decision 2). Decided in the slice 05 plan.
3. **Row-level security.** Revisit when auth arrives.
4. **J11 details.** The author column on `context`, and whether `outcome` should also be per person.
