# ADR-001: Initial technology stack and baseline

- Status: Proposed. The database choice is superseded by ADR-002 (Postgres on Neon); the rest stands.
- Date: 2026-11-05

## Context and problem statement

What technology stack should Moneo start with, given where the project is now and the constraints I'm working under?

### Current state

- Agentic personal finance web app, v1 in progress
- Bank statements (CSV and PDF) and receipt photos imported
- Public demo link with demo data for recruiters

### Constraints

1. **Storage and auth:** data is stored in a database, accessed through a backend. No authentication in the first demo version; auth will be added afterwards. Until then, the deployed app holds demo data only, never real bank statements.
2. **CSV, PDF and images supported:** the app should be able to interpret information from multiple types of data, either as bank statements or single photo of receipt.
3. **Money:** GBP only, stored as integer pence.
4. **Performance:** handle at least 12 months of transactions (roughly 3–5k rows) without the UI freezing.
5. **Invalid input:** reject invalid files gracefully, and guard against other interactions that could put the app into an invalid state.
6. **Familiar tools:** use my existing knowledge of React, Next.js, TypeScript and Tailwind CSS. Vite + React is an option, but its suitability for this project needs discussing.
7. **Customisable components:** use a component library I can customise if I need to. I would want to be able to import components as I need them, so shadcn is an option here.
8. **Validation:** strict TypeScript, plus Zod at every boundary: CSV rows, data read from storage, and API requests/responses.
9. **Testability:** pure logic kept separate from React, with Vitest unit tests for each function.
10. **Deployment:** must be easy to deploy after each change; Vercel is preferred.

## Decision

- **Language:** TypeScript (strict mode)
- **UI:** React with Tailwind CSS
- **Framework:** Next.js. With a database, API routes or server actions give the backend without a separate service.
- **Component library:** shadcn/ui
- **Validation:** Zod (I will have to better understand where we will need this aside from rows)
- **File import:** CSV, PDF and receipt images extracted via AI, validated with Zod and confirmed by the user before saving.
- **Money:** integer pence, GBP only
- **Testing:** Vitest, with business logic in pure functions outside React
- **Hosting:** Vercel
- **Database:** Neo4j (AuraDB) for all app data. Moneo's core idea is the connection between spending, moods, motivations, habits and goals, which maps naturally onto a graph. Also a learning goal.
- **State management:** deferred (see open decisions)
- **Agent orchestration:** LangGraph.js (with LangChain.js building blocks), running in Next.js server routes. Chosen as a learning goal: I want hands-on experience building agentic workflows. Docs: docs.langchain.com/oss/javascript/langgraph

## Consequences

- **Good:**
  - The UI layer builds on tools I already know, so I can move quickly there under time pressure
  - Strict types, Zod and pure-function tests make the logic easy to trust and refactor
  - Next.js API routes would give the backend without a separate service
  - A database makes cross-device access and joint finances feasible (for the future, when the app will have auth), and API keys will live in the server
  - Questions about the "why" behind spending become natural graph queries, following connections between transactions, moods, motivations, habits and goals

- **Bad / trade-offs accepted:**
  - GBP only, so no multi-currency support
  - I am not familiar with LangChain, so this might take some time to understand it
  - I am now responsible for securing stored financial data, which means more infrastructure to build and maintain
  - Using a different type of database, I will need to get familiar with that too
  - Using AI means I need to be aware of token usage, and potentially limit usage if a user is trying to overuse my demo app, so I need to come up with a solution for that
  - Without auth, anyone with the demo link can read and change the data, so real financial data must stay off the deployed app until auth is in place

## Open decisions (to be recorded as future ADRs)

1. **Data model:** how transactions, merchants, moods, motivations, habits, goals, rules and categories are modelled in the database (originally nodes and relationships in Neo4j; now Postgres tables, see ADR-002). To be recorded as ADR-003.
2. **Authentication (after the first demo):** which provider or library, and how the demo is kept separate from real data. Also: joint finances for me and my partner on our own devices (SPEC J11) are deferred until auth exists, and so is any real data on the deployed app.
3. **App states:**
   - App level: is there any data to show? If not, do we show the demo features? Should there be an option to reset the data for demo purposes?
   - CSV, PDF and image upload flow states
   - View states (transaction list, behaviour charts)
   - States for each transaction

   **Answered in SPEC.md (States section), decisions D-005, D-009, D-010, D-027 to D-030, D-033. Waiting to be recorded as an ADR.** Why it is answered: writing the user journeys forced each state to be named, and every one is needed by a journey or a Gherkin scenario.
   - App level: empty, populated, resetting, error. With no data the user sees "Load demo data" and "Import a statement" (in demo mode, only the sample files). Reset exists in demo mode only and wipes the visitor's own copy (D-030). Each demo visitor has their own copy, expiring after 24 hours of inactivity (D-005).
   - Upload flow: `idle`, `validating`, `extracting`, `reviewing`, `saving`, `saved`, with `rejected`, `failed` and `cancelled` as the other endings. Rows inside review are `valid`, `needs-fix`, `duplicate` or dropped by the user, and only valid rows are saved.
   - View states: `loading`, `empty`, `filtered-empty`, `populated`, `partial` (some transactions uncategorised), `error`.
   - Transaction: category source (`uncategorised`, `ai`, `user`) and context (`none`, `partial`, `complete`). The "excluded" flag was dropped (D-007).
   - Still open inside this decision: what survives a refresh during review (open decision 17).
4. **Categorisation rules:** (partly answered: the AI categorises by unique merchant, picks from a fixed category list or answers "unknown", and categorisation happens before review, see D-002, D-012, D-020, D-022. Still open: whether a merchant library is added, and the token and cost trade-offs, see open decisions 14 and 15.) What do we use to categorise expenses? Use a library of merchants? Make use of AI exclusively? What considerations are most important here? Tokens, performance, or how architecturally maintainable this is?
5. **Manual overrides:** do we allow that, and if so, how does validation happen here?

   **Answered in SPEC.md, decisions D-006, D-007, D-021, D-023. Waiting to be recorded as an ADR.** Why it is answered: the category override and context journeys (J6, J7) cannot be written without deciding which fields can change, and the choice turned out to be small.
   - Allowed: category and context (mood, motivation, outcome, each a value from a fixed list plus an optional note), and date, amount and raw description.
   - Also allowed, added later (D-034): date, amount and raw description, because the AI can misread a file. The original imported values are kept on the transaction for duplicate matching and to show an "edited" marker. There is still no manual entry of new transactions (D-018).
   - Validation: Zod on every edit: the fixed category and context lists, a maximum length on notes, amount as integer pence and date as a real date. A bad value is rejected and the old value is kept.
   - A category override can be applied to the other stored transactions of the same merchant on request, with one undo for the whole batch. It is not remembered for future imports in v1 (D-021).

6. **Security:** what security concerns apply, now that data lives on a server? (TODO: research)
7. **Undo and editing:** do users get undo for certain actions, or only the ability to edit carefully chosen fields?

   **Answered in SPEC.md, decisions D-021, D-030, D-033. Waiting to be recorded as an ADR.** Why it is answered: the edit journeys needed a rule for mistakes, and the cheapest safe rule covers every edit the user can make.
   - Only category changes (including the same-merchant batch), edits to date, amount and description, and clearing a context field have undo, as a short-lived undo of 10 seconds, with the length in the config file.
   - There is no general undo stack. Import is protected by the review step before saving, so it needs no undo. Reset is not undoable, and it asks for confirmation instead.
   - Editing is limited to the fields in decision 5, so there is nothing else to undo. Edits to date, amount and description join the 10-second undo (D-034).

8. **State management:** Zustand, Jotai, or React state/context. To be decided once I have a better overview of the project, and after getting familiar with Zustand/Jotai.
9. **Agent memory:** a separate store for LangGraph checkpoints, since there's no ready-made Neo4j checkpointer (to be decided and learn more about that). With Postgres (ADR-002) the checkpoints could live in the same database; still to be decided.
10. **Multimodal AI model:** what is it and how is it different from a traditional OCR solution here? What cost considerations are there and what complexity does this add to the app? This is relevant for parsing uploaded files.
11. **Finance education:** how the UK finance guides (budgeting, private pensions, investment types, HMRC benefits, mortgages) are produced and delivered. Options include static written content, AI-generated guides, or a mix, and the choice affects how guides are tied to a user's spending behaviour. The user journeys for this are deliberately not yet written in SPEC.md.
12. **CSV parsing approach:** CSV is read by a deterministic parser (fixed rules, integer pence, no AI on amounts), not by the AI. Decide how the parser learns each bank's column layout: (a) hand-written presets per bank (RBS first), (b) AI mapping, where the model looks at the header and a few sample rows once per file and proposes which column is date, amount and description, the user confirms, and the parser does the rest, or (c) presets first with AI mapping as the fallback for unknown layouts. AI mapping is wanted partly as a learning goal. Also decide whether the AI categorises by unique merchant (cheaper than by row) and what the confirm-the-mapping step looks like. Relates to open decisions 4 and 10.
13. **Checking AI extraction against the source:** v1 gives no help comparing extracted rows with the original file; the review screen and optional balance check are the only safeguards, and I accept the risk of AI misreads for now. Decide later whether to add (a) a page reference on each extracted row, (b) the original shown beside the rows with click-to-highlight (needs the model to return positions, and a viewer), or (c) the original in a pane without highlighting. Relates to open decision 10.
14. **AI confidence and reliability:** I need to understand what "confidence" means for an LLM before relying on it. Learn and decide: why a model's self-reported confidence score is unreliable, what alternatives exist (the model answers "unknown", structured output with a fixed category list, multiple runs that must agree, logprobs where a provider exposes them, checks in code such as the balance check), and where each applies: categorisation, column mapping (open decision 12), and PDF/receipt extraction (open decision 10). For now categorisation uses "pick a category or answer unknown", with no confidence score. Relates to open decisions 4 and 10.
15. **Merchant identity:** how two raw bank descriptions are recognised as the same merchant (for example "TESCO STORES 3214" and "TESCO EXPRESS"). Options: normalise in code, have the AI assign a clean merchant name, or both. v1 uses code normalisation only (digits and reference numbers stripped, lower-cased, exact match); the upgrade to evaluate is both together, normalising in code first and then having the AI name the merchant. Affects categorising by unique merchant, "apply to the same merchant" overrides, and the Merchant node in the data model (open decision 1).
16. **Demo mode / user mode switch:** the app runs in two modes, demo mode (sample files only, per-visitor demo data, checklist, usage limits) and user mode (real file picker, one shared dataset), controlled by a feature flag. The same mechanism should also hold per-visitor limit overrides (SPEC D-008), so a limit can be changed for one person quickly. Decide the flag mechanism: an environment variable (simple, but changing it on Vercel needs a redeploy), a managed flag service such as Vercel Edge Config (changes instantly), or a value in the database. Decide also where the flag is read so that no demo or user code path can be reached in the wrong mode, and how to make sure user mode can never be switched on in the public deployment by accident.
17. **Surviving a refresh during import review:** in v1, refreshing or closing the page during review loses the review, and a 4,000-row review lost by accident will hurt a real user. Decide whether to save the review as a draft (where: server database, or browser storage), how long a draft lives, what happens to a draft when the user starts a second import, and how drafts are cleaned up in demo mode (per-visitor, expiring). Relates to open decision 3 (upload flow states).
18. **Editable data table:** transactions are shown in a table that must support inline editing of date, amount, description, category and context (SPEC D-034), in review and on stored transactions, with about 5,000 rows and without the UI freezing (constraint 4). shadcn/ui's Table is only styled HTML, so editing and virtualisation are not included. Options: (a) TanStack Table (headless, the base of shadcn's Data Table recipe) with TanStack Virtual and shadcn inputs as click-to-edit cells, so only the cell being edited renders an input; (b) a ready-made grid with editing and virtualisation built in, such as react-data-grid, at the cost of styling that does not match shadcn; (c) a heavy grid such as AG Grid, with features I do not need and a paid tier. TanStack Table with TanStack Virtual is chosen (D-034); a small spike still verifies it. Spike: build a 5,000-row table with one editable column, Zod validation on commit, and keyboard navigation, and measure it before committing. Also decide how selection, row-state filters and bulk actions (SPEC J5) fit the same table.
