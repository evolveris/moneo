# ADR-002: Database: Postgres on Neon, replacing Neo4j

- Status: Proposed
- Date: 2026-11-13
- Supersedes: the Database line of ADR-001

## Context and problem statement

ADR-001 chose Neo4j AuraDB for all app data. The reasons given were that Moneo's core idea is the connection between spending, moods, motivations, habits and goals, which "maps naturally onto a graph", and that learning a graph database was a goal. Before writing the data model (ADR-001 open decision 1), a senior engineer asked whether a relational database would do the same job. This ADR records the answer.

### What we checked

- **LangGraph does not need Neo4j.** LangGraph's "graph" is a workflow (steps and the order between them), not a graph database. It needs somewhere to keep checkpoints only if runs must be resumable, and there is no ready-made Neo4j checkpointer (ADR-001 open decision 9).
- **The data is a star, not a network.** Every relationship in the current plan is one hop from the transaction: merchant, category, mood, motivation, outcome, context, import, derived AI label. Graph databases are strongest at variable-depth traversal, path finding and relationship types that are not known in advance. None of the specified journeys needs those.
- **The queries are aggregations.** Spend per category per month, spend by mood and outcome, and the other chart queries are grouped sums with a join. We wrote five real operations side by side in Cypher and SQL (spend per category per month, spend by mood split by outcome, a same-merchant category change with undo, deleting a transaction with its context, wiping one visitor). The first two were equal, the third slightly favoured Cypher, and the last two favoured SQL.
- **Cleanup and isolation are safer in SQL.** In Postgres a cascading foreign key removes a transaction's context, and a visitor's whole data, with one declared rule. In Neo4j, `DETACH DELETE` removes relationships but leaves child nodes behind unless every query names them, so each new kind of child (derived AI labels, receipt lines) must be remembered in every delete query. Postgres can also enforce visitor isolation in the database with row-level security; Neo4j has no equivalent, so a forgotten visitor filter is a data leak.
- **Postgres has constraints.** Foreign keys, `NOT NULL` and `CHECK` rules reject bad data inside the database as well as in Zod.

## Decision

- **Database:** Postgres, hosted on Neon. Replaces Neo4j AuraDB.
- **Access:** plain SQL through a Postgres driver, called only from server code. One module, `src/lib/db.ts`, creates the connection and is the only place that imports the driver; a lint rule enforces it, as it does today for `neo4j-driver`. Data functions wrap the queries, so a later change of database or query layer touches few files.
- **Configuration:** one variable, `DATABASE_URL`, parsed with Zod in `src/lib/env.ts`. No `NEXT_PUBLIC_` prefix.
- **Development database:** Neon branches. A `dev` branch is used locally and `main` is used by the deployed app, so local work cannot write into the deployed data. This answers the "decide the dev database" gate in `docs/slices/README.md`. A branch per pull request is optional and off by default; check the Free plan's branch limit on Neon's pricing page before turning it on, because branches beyond a plan's allowance are billed on paid plans.
- **Visitor isolation:** every query for demo data filters by visitor (AGENTS.md). Whether to add row-level security as a second layer is decided in ADR-003.
- **Money:** integer pence in an `integer` column (up to about £21 million), read back as a plain JavaScript number.
- **Graph databases later:** not ruled out. If the habits and goals idea (ADR-001) turns out to need multi-hop questions, a graph can be added next to Postgres, behind the same data functions.

## Consequences

- **Good:**
  - Cascading deletes and constraints, declared once in the schema.
  - One place can hold both app data and LangGraph checkpoints (to be decided in ADR-001 open decision 9).
  - Standard tooling: migrations, a typed query layer if wanted, Vercel integration, and widely transferable SQL skills.
  - The Neo4j driver's `Integer` type no longer needs converting at the boundary.
  - Separate dev and deployed databases without extra setup.
- **Bad / trade-offs accepted:**
  - The graph-database learning goal is dropped for now.
  - Slice 02 (the Neo4j connection and health check) is redone as slice 02b. The code involved is small.
  - Free-tier limits of the hosted service apply (storage, compute, branches, idle behaviour). They must be checked against the demo's needs, because a recruiter may open the link after weeks of inactivity.
  - Queries that follow a long chain of connections would be harder in SQL than in Cypher. None is planned.

## Open decisions (to be recorded later)

1. **Query layer:** raw SQL first, or a TypeScript-first layer such as Drizzle. Proposed: raw SQL for the first slices, so every query is visible; revisit when migrations or typing become a burden.
2. **Migrations:** how schema changes are written and applied, and who runs them on `dev` and `main`.
3. **Row-level security:** whether to use it on top of the visitor filter. Decided together with the data model (ADR-003).
4. **Idle behaviour:** what the app shows if the database is slow to wake after being idle, and whether the health check needs to handle it.
